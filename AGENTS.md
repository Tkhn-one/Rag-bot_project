# AGENTS.md — правила работы в этом репозитории

Учебный проект по дисциплине **«ООП. Современные паттерны»** (проектная траектория, Москва, 2026).
Полные требования преподавателя — в `docs/METODICHKA.md`. Читать её перед началом любой задачи.
Требования методички имеют приоритет над привычными практиками разработки.

Codex подхватывает этот файл автоматически (иерархия: глобальный `~/.codex/AGENTS.md` → корневой `AGENTS.md` → вложенные).
Раздел «Стек и команды» дополняется реальными командами проекта.

---

## 1. Проект

- **Название:** RAG-чатбот по документам — десктопное приложение (рабочее название)
- **Продукт:** приложение для обычного пользователя: PDF/DOCX/TXT → ответы с цитатами. Одна кодовая база — две сборки: THIN (внешний API) и FAT (встроенная llama, офлайн).
- **Основной пользователь MVP:** руководитель проектов организации N, который сопоставляет ТЗ с договором и ищет сведения о принятых, выполненных и отложенных решениях в документах проекта. Организация N — условное обозначение; этот фокус не ограничивает использование приложения другими людьми.
- **Постановка задачи:** `docs/PROJECT_BRIEF.md` — читать первым.
- **Требования преподавателя:** (1) платформа для обычного пользователя, не «питон-бэкендер»; (2) кэш повторных вопросов, чтобы не расходовать API; (3) два варианта приложения — внешний API и локальная llama; (4) выбор нейросети; (5) монетизация (студентом выбрана разовая покупка и ключ пользователя); (6) документы, которые нельзя передавать третьим лицам, обрабатываются только локально.
- **Текущий этап:** 2 — архитектура. Заявка и объём приняты преподавателем 15.09.2026, уровень — продвинутый; подтверждено студентом 06.10.2026. Описание продукта этапа 1 утверждено студентом и фиксируется версией `v0.1`; отдельное предъявление этой редакции преподавателю не зафиксировано. Состояние и следующие действия в `docs/ROADMAP.md`.

## 2. Стек и команды

**Выбрано студентом 17.09.2026: C++20 + CMake + Qt 6.** Python и веб-оболочка не выбраны.

Стек ещё не реализован: в репозитории нет исходного кода, `CMakeLists.txt` и тестов. Команды ниже — плановые; имена целей и пути запуска будут проверены при создании прототипа.

- Язык: C++20 (минимум по методичке — C++11), система сборки CMake
- GUI: Qt 6, только слой Presentation; подробности интеграции и распространения определяются на этапе 2
- Сборка: `cmake -S . -B build && cmake --build build`
- Тесты: `ctest --test-dir build --output-on-failure`
- Запуск: `./build/app` (Windows: `build\Debug\app.exe`)
- Форматирование: `clang-format -i`

## 3. Обязательные правила (следствия из методички)

1. **Один коммит = одно законченное логическое изменение.** Сообщение описывает **результат**, а не процесс.
   - Хорошо: `Добавлен импорт транзакций из CSV`, `Исправлено двойное сохранение заказа`, `Выделен интерфейс IReportExporter`, `Добавлены тесты пограничных дат` (с тегом `тесты`).
   - Плохо: `код`, `fix`, `переделал классы`, `тесты`.
2. **Никогда не имитировать историю Git**: не переписывать прошлые коммиты, не менять даты, не подгонять число коммитов. Это прямо запрещено (п. 7.2 методички).
3. **Никаких секретов в репозитории**: ключи, токены, `.env`, персональные данные. Проверяй `git status` перед коммитом.
4. **Не оставляй несобираемый код.** После каждого законченного изменения: собрать + прогнать тесты + обновить `CHANGELOG.md`.
5. **После существенного эпизода** (архитектурное решение, ошибка ИИ и её разбор) — предложить запись в `docs/AI_LOG.md` и решение — в `docs/DECISIONS.md`.
6. **Каждый класс должен иметь объяснимую ответственность.** Искусственные классы «ради количества» не допускаются.
7. **Объясняй свои решения.** Для каждого неочевидного шага: что выбрано, какие альтернативы, почему. Студент защищает проект устно и должен понимать каждую строку.

## 4. Архитектурные правила

Это ограничения и рабочие ориентиры проекта, а не перечень отдельно утверждённых преподавателем технологий. Статусы решений берутся из `docs/DECISIONS.md`; наличие правила здесь не переводит предложенный ADR в принятый и не разрешает установку зависимости.

- Слои: **Domain** (сущности и правила, без UI и БД) → **Application** (сценарии) → **Infrastructure** (файлы, JSON/SQLite, сеть, логирование) → **Presentation** (CLI, затем GUI) → **Tests** (независимо от интерфейса).
- **Композиция — основной способ построения объектов.** Наследование — только с обоснованием.
- **Полиморфизм:** минимум один оправданный пример через интерфейс/абстрактный класс. В этом проекте он задан темой:
  - `ILlmProvider` — реализации `RemoteApiProvider` (OpenAI-совместимый: GPT/DeepSeek/Grok/OpenRouter) и `LocalLlamaProvider` (llama.cpp, офлайн), плюс `MockProvider` для тестов;
  - `CachingLlmProvider` — **декоратор** над `ILlmProvider`, отвечает за кэш;
  - стратегии чанкинга/поиска и экспорта — по необходимости.
- **Кэш — продуктовое требование, а не оптимизация.** Правило: один и тот же вопрос при неизменном индексе не должен приводить к сетевому вызову. Ключ кэша = hash(нормализованный вопрос + версия индекса + id модели). Инвалидация — при изменении документов или модели. Любая новая фича, генерирующая вызовы к API, обязана проходить через кэш.
- **Две сборки, один код:** опция CMake `WITH_LOCAL_LLM=ON/OFF` (THIN/FAT). Бизнес-логика и Domain не должны знать, какой провайдер включён.
- **GUI — расширение, а не замена архитектуры.** Замена CLI на GUI не должна требовать правок бизнес-логики. Если требует — это архитектурный дефект, сообщи об этом, а не «поправь логику под UI».
- **Секреты:** API-ключи только из системного хранилища или переменных окружения, никогда в коде, логах и репозитории; в логах ключи маскируются.
- **Приватность — продуктовое требование, а не настройка.** Инвариант: *текст документа может покинуть машину только при активном удалённом провайдере и явном разрешении пользователя на отправку этого документа*. Правила:
  - у библиотеки/документа есть политика `LocalOnly` | `AllowRemote` (по умолчанию `LocalOnly` для помеченных пользователем);
  - проверка политики — **в одном месте** (Application при выборе провайдера), а не по всему коду;
  - попытка обработать `LocalOnly`-документ удалённым провайдером — это **ошибка с понятным сообщением**, а не «предупреждение и продолжить»;
  - при активном локальном провайдере приложение не делает исходящих сетевых запросов вообще (кроме явно запрошенного пользователем скачивания модели);
  - содержимое документов и ответов **не пишется в логи**; телеметрия по умолчанию выключена;
  - тест «ноль сетевых вызовов» обязателен для локального режима.
- **Инкапсуляция:** приватное состояние, минимальный публичный интерфейс, никаких публичных полей без причины.
- **Ошибки:** некорректный ввод и ожидаемые сбои (пустой файл, битый PDF, нет прав, нет сети, неверный API-ключ) обрабатываются; программа не должна аварийно завершаться в обычных сценариях.

## 5. Рабочий процесс по этапам

| Этап | Результат | Фиксация |
|---|---|---|
| 0. Выбор темы | Заявка на проект | документ заявки |
| 1. Product brief | `docs/PRODUCT.md` | тег `v0.1` |
| 2. Архитектура | `docs/ARCHITECTURE.md`, `docs/DECISIONS.md` | тег `v0.2` |
| 3. Вертикальный прототип | один сценарий через все слои + тест | тег `v0.3` |
| 4. Рабочее ядро | основные сценарии, обработка ошибок, сохранение, тесты | тег `v0.5` |
| 5. MVP | удобный запуск, демо-данные, документация | тег `v0.9` |
| 6. Защита | репетиция вопросов, мелкие правки | тег `v1.0` |

Не перескакивай этапы и **не реализуй функциональность будущих этапов без явной просьбы**.

## 6. Что делать, когда пользователь даёт задачу

1. Если задача неоднозначна — задай уточняющий вопрос, не угадывай.
2. Сверься с `docs/METODICHKA.md` и укажи, какие пункты затрагивает задача.
3. Если решение архитектурно значимо — предложи **2–3 варианта** со плюсами/минусами и рекомендацией.
4. Реализуй **минимум**, достаточный для текущего этапа.
5. Прогони сборку и тесты, покажи команды и результат.
6. Предложи текст коммита (описывающий результат) и запись в `AI_LOG.md`, если эпизод существенный.
7. Не коммить и не пушь без подтверждения пользователя.

## 7. Запрещено

- `git push --force`, `git reset --hard` на `main`, удаление тегов, `commit --amend` для уже отправленных коммитов.
- Добавлять внешние зависимости без согласования.
- Рефакторить код за пределами текущей задачи «заодно».
- Генерировать документацию «на будущее» без запроса.
- Отправлять куда-либо секреты, токены и персональные данные пользователя.
- Выдавать непроверенный код за работающий: если не собирал и не тестировал — так и напиши.

## 8. Готовность к защите

Для каждого существенного изменения держи наготове короткое объяснение:
- почему этот класс существует отдельно и что он делать не должен;
- где используется полиморфизм и какую проблему решает;
- почему выбрана композиция, наследование или конкретный шаблон;
- как заменить хранилище, не переписывая предметную логику;
- какую ошибку допустил ИИ и как она была обнаружена;
- как восстановить последнюю стабильную версию (`git checkout v0.5`, `git log`, `git bisect`).
