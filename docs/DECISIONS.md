## ADR-001 — Язык и стек проекта

- **Дата и статус:** 17.09.2026 — **принято студентом**
- **Контекст:** методичка требует C++11+; другие языки допустимы только по согласованию с преподавателем. Предшествующий прототип реализован на Python (Streamlit).
- **Рассмотренные варианты:**
  1. C++20 + CMake — соответствует языку и системе сборки по умолчанию методички; потребует освоения C++ и интеграции зависимостей.
  2. Python — позволяет использовать идеи предыдущего прототипа, но требует отдельного согласования языка и условий курса.
- **Решение:** C++20 + CMake, по прямому выбору студента в текущем обсуждении. Python для этой кодовой базы не выбран.
- **Причины:** обоснование в проекте — соответствие курсу ООП на C++ и совместная разработка ядра и Qt-интерфейса на выбранном языке. Это не утверждение, что C++ автоматически обеспечит лучшую скорость RAG.
- **Последствия:** первый прототип и тесты создаются на C++; потребуется проверить компилятор и сборку. Это не завершает этап 2 и не означает наличие `CMakeLists.txt` или установленных зависимостей.

## ADR-002 — Слои и внедрение зависимостей

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** CLI должен заменяться GUI без переписывания бизнес-правил; нужен тестируемый C++-проект.
- **Рассмотренные варианты:**
  1. Domain / Application / Infrastructure / Presentation с портами — явные границы и независимые тесты, больше интерфейсов на старте.
  2. Монолит — проще первый запуск, но UI, сеть и правила быстро связываются.
  3. Отдельный сервер и GUI-клиент — независимое развёртывание, но лишние процессы и протокол для локального приложения.
- **Решение:** Слои; порты в Application; реализации в Infrastructure, композиция в apps. Domain и Application без Qt, SQLite и llama.cpp.
- **Причины:** Соответствует разделам 4–5 методички; позволяет менять провайдера и хранилище отдельно от сценариев.
- **Последствия:** Точные обязанности и контракты перечислены в ARCHITECTURE.md. В прототипе создаются только нужные классы; каталог абстракций заранее не генерируется.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-003 — Платформа GUI

- **Дата и статус:** 17.09.2026 — **принято студентом**
- **Контекст:** преподаватель требует приложение для обычного пользователя (не «питон-бэкендер»); язык курса по умолчанию C++11+; GUI по методичке — расширение архитектуры, а не замена.
- **Рассмотренные варианты:**
  1. **Qt 6 + CMake (C++)** — интерфейс на выбранном языке; потребуется проверить сборку, упаковку и условия распространения зависимостей.
  2. **Tauri/Electron + C++ ядро** — возможность веб-интерфейса, но смешанный тулчейн и дополнительная интеграция.
  3. **PySide6 (Python)** — возможность использования Python, но язык не выбран и требует согласования.
- **Решение:** Qt 6 поверх C++20-ядра, сборка CMake; прямой выбор студента в текущем обсуждении. На 17.09.2026 Widgets/QML, версии и упаковка ещё не определялись; уточнение от 26.10.2026 — Qt Widgets и поставка для Windows по ADR-012.
- **Причины:** обоснование в проекте — настольный интерфейс для обычного пользователя и единый выбранный C++-стек без веб-оболочки.
- **Последствия:** Qt используется только в Presentation; GUI не меняет правила предметной области и качество ответов. Выбор способа поставки и проверка источников лицензий описаны в ADR-012; фактический комплект проверяется при интеграции; один автономный бинарник и готовая поддержка ОС не обещаются. Установка Qt этим решением не выполняется.

## ADR-004 — Провайдер ответа и THIN/FAT

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** Нужны внешняя и локальная генерация, выбор модели, тесты без сети. Студент 26.10.2026 выбрал первым сервисом OpenAI.
- **Рассмотренные варианты:**
  1. ILlmProvider и две реализации в одной базе — единые правила и тесты; нужно связать адаптеры.
  2. Две кодовые базы — изолированная поставка, но дублирование кэша и приватности.
  3. Локальный сервер Ollama/llama-server — удобен для экспериментов, но добавляет процесс, настройку и сетевой интерфейс.
- **Решение:** ILlmProvider: RemoteApiProvider (OpenAI Responses API), LocalLlamaProvider (встроенная llama.cpp), MockProvider. WITH_LOCAL_LLM включает только локальную генерацию; общий движок эмбеддингов есть в обеих поставках. Сеть — WinHTTP, формат — nlohmann/json. Начальный удалённый профиль gpt-5.4-mini-2026-03-17, выбор модели — настройка.
- **Причины:** Один сценарий получает провайдера через композицию. Встроенный runtime не требует терминала или фонового сервера. Responses API выбран под первый сервис, универсальная совместимость с другими сервисами не обещается.
- **Последствия:** FAT включает генератор и веса; THIN — без них. Модель/endpoint/параметры входят в идентичность кэша. Доступ OpenAI проверяется при интеграции без отправки закрытых документов. Веса и runtime пока не скачиваются. Ссылки на API и карточку модели — в ARCHITECTURE.md, разделы 8–9.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-005 — Кэш и проверка ответа

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** Повтор завершённого вопроса при неизменных индексе и модели не должен вызывать платный API. Неверные цитаты не должны попадать в кэш.
- **Рассмотренные варианты:**
  1. CachingLlmProvider как декоратор — общий для локального и внешнего режима, легко проверяется счётчиком; требует отдельного порта хранения.
  2. Кэш внутри RemoteApiProvider — меньше классов, но смешивает сеть и хранение и не работает для локальной модели.
  3. Кэш в GUI — быстро показать, но обходится CLI и привязывает бизнес-правило к интерфейсу.
- **Решение:** CachingLlmProvider(ValidatingLlmProvider(realProvider)). AnswerCache строит ключ и использует IAnswerCacheStore. Политика проверяется в RagService до чтения кэша. Только успешные структурно проверенные ответы сохраняются в SQLite.
- **Причины:** Декораторы имеют разные обязанности; интерфейс UI не влияет на экономию вызовов. Совпадение текста цитаты проверяемо без второго LLM-вызова.
- **Последствия:** Ключ — hash(нормализованный вопрос + версия индекса + id модели). Ревизия включает библиотеку и меняется также при изменении политики, поиска и инструкций; модель включает endpoint/веса/параметры. История не участвует: вопросы самостоятельны. Смена ключа меняет пространство профиля, без записи секрета. Ошибки/отказы не кэшируются; повтор после неопределённого сетевого сбоя только вручную. Проверка цитаты не доказывает смысловую правильность.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-006 — SQLite и точный поиск по сохранённым векторам

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** Нужны локальное сохранение, согласованное обновление текста, индекса, кэша и истории. 30 файлов — ориентир, не точное число чанков и не предел.
- **Рассмотренные варианты:**
  1. SQLite + FTS5 + векторы BLOB, точный перебор — одна транзакционная система и минимум зависимостей; стоимость поиска растёт линейно.
  2. SQLite + hnswlib/usearch/FAISS — быстрее для больших индексов, но отдельный индекс надо согласованно обновлять и восстанавливать.
  3. ChromaDB или другой отдельный сервер — готовый сервис поиска, но дополнительная установка и процесс.
- **Решение:** SQLite хранит канонические текст/позиции, FTS5, float32-векторы, историю и кэш. Для MVP — точный cosine search блоками, без ANN-библиотеки. Копии исходников — рядом с БД под служебными ID.
- **Причины:** Для предполагаемой нагрузки сначала важнее простота целостного сохранения. Достаточность скорости проверяется, не выводится только из числа файлов.
- **Последствия:** Прежнее предложение об отдельном файле векторного индекса не выбрано. Публикация ревизии транзакционная; файлы записываются до публикации ссылок. Контракты IKnowledgeStore/IAnswerCacheStore/IHistoryStore позволяют заменить адаптер. Если измерения выявят проблему, новый ADR обосновывает ANN; текущий документ не обещает масштабирование без предела.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-007 — Модель монетизации: разовая покупка + ключ пользователя

- **Дата и статус:** 15.09.2026 — **принято**, дата и решение подтверждены студентом в обсуждении
- **Контекст:** у части пользователей документы нельзя передавать третьим лицам, поэтому нужен офлайн-режим; при этом продавать подписку со своими ключами сейчас нельзя — ключи, зашитые в десктопный клиент, извлекаются, а сервер-прокси требует отдельной инфраструктуры.
- **Рассмотренные варианты:**
  1. **Разовая покупка + ключ пользователя (BYO-key)** — вендор не платит за API-токены пользователя, локальный режим не требует оплаты API.
  2. Подписка с вендорским API — нужен сервер-прокси и защита ключей; расход на токены попадает в себестоимость.
- **Решение:** вариант 1. Вариант 2 — вне рамок текущей версии. Уточнение от 06.10.2026: студент выбрал ценовую гипотезу **15 000 ₽ за лицензию**. Готовность платить и окончательная цена проверяются после MVP; условия лицензии и обновлений ещё не определены.
- **Причины:** вендор не оплачивает API-вызовы пользователя; конфиденциальные документы могут обрабатываться офлайн; сервер для вендорского API не входит в MVP. Затраты на разработку, поддержку и распространение не считаются нулевыми.
- **Последствия:** пользователю внешнего режима потребуется получить свой ключ; нужен понятный онбординг. Кэш (ADR-005) экономит API-запросы. Основание ценовой гипотезы — регулярный поиск и проверяемость ответа по источнику; после проверки продукта потребуется оценка экономии времени и готовности пользователя платить; локальная работа требует ресурсов ПК, даже без оплаты API.

## ADR-008 — Границы доверия и режим «Только локально»

- **Дата и статус:** 15.09.2026 — **принято**, дата и решение подтверждены студентом в обсуждении
- **Контекст:** часть документов запрещено передавать третьим лицам. Продукт обязан физически, а не декларативно, гарантировать, что такие документы обрабатываются локальной моделью.
- **Рассмотренные варианты:**
  1. **Политика обработки у библиотеки/документа** (`LocalOnly` / `AllowRemote`), проверяемая в единственной точке выбора провайдера в Application-слое; попытка нарушить политику — ошибка с понятным сообщением.
  2. Предупреждение в UI («вы уверены?») — отвергнуто: при «защите от дурака» предупреждения обходятся по привычке.
  3. Разные сборки с разным кодом — отвергнуто: дублирование логики, риск регрессии.
- **Решение:** вариант 1. Содержимое документов не попадает в логи; телеметрия выключена по умолчанию; хранение ключа конкретизировано 26.10.2026 в ADR-009. Обязателен автоматический тест «ноль сетевых вызовов» при локальном провайдере.
- **Причины:** проверяемость. На защите продукт демонстрируется через монитор сети: документ «только локально» — ни одного исходящего соединения.
- **Последствия:** нужен слой политики поверх `ILlmProvider` (в Application), он же используется для отображения статуса в UI («документ закрыт: обрабатывается на этом компьютере»); любая новая функция с сетевыми вызовами обязана уважать политику.

## ADR-009 — Хранение API-ключа на Windows

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** Для проекта выбраны Windows 10/11. Обычный пользователь должен вводить ключ в интерфейсе, без открытого файла и терминала.
- **Рассмотренные варианты:**
  1. Windows Credential Manager — системное хранение и нативный API; привязка к Windows и учётной записи.
  2. Открытый конфигурационный файл — просто читать, но неприемлемо для ключа.
  3. Переменная окружения — полезна для разработки, неудобна для обычного пользователя.
- **Решение:** WindowsCredentialStore за портом ISecretStore, ключ по идентификатору профиля. Переменная окружения — только явный режим разработки; не скрытый запасной путь при ошибке системного хранилища.
- **Причины:** Платформа уже выбрана; отдельная кроссплатформенная библиотека секретов не нужна.
- **Последствия:** Ошибка сохранения видна пользователю. Ключ не попадает в БД/экспорт/логи; в GUI по умолчанию скрыт. Хранилище не защищает от любого процесса той же учётной записи. Никаких реальных ключей для этапов 2–3 не требуется.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-010 — Извлечение текста и неизменяемые источники

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** Форматы PDF/DOCX/TXT обязательны, цитаты должны вести к реально прочитанной версии. OCR вне MVP.
- **Рассмотренные варианты:**
  1. PDFium + miniz/pugixml + собственный простой TXT-reader — работают внутри приложения, но требуют адаптеров и проверок сборки.
  2. Внешние утилиты конвертации/LibreOffice — быстро использовать готовые инструменты, но усложняют поставку и запуск.
  3. Облачное распознавание — упрощает часть форматов, но нарушает локальный режим и добавляет стоимость.
- **Решение:** Первый вариант за IDocumentReader. Сохранять локальную копию файла и текст с координатами; документ публиковать только после завершения обработки. Для DOCX использовать абзацы/ячейки, не выдумывать страницы.
- **Причины:** Позиции формирует reader, не модель. Изменение исходного файла не меняет сохранённую цитату.
- **Последствия:** PDFium без JS/XFA; DOCX без внешних ссылок и исполнения. Неподдержанный/нетекстовый контент отмечать явно. Возможны ошибки чтения сложной вёрстки. TXT в этапе 3; сторонние парсеры — в этапе 4. Проверить лимиты распаковки, лицензии, ошибки и источник бинарных сборок.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-011 — Гибридный локальный поиск и модели

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** Нужно искать русские формулировки и точные номера пунктов. На проверенном ПК Ryzen 5 7640HS, около 15,2 ГиБ RAM и встроенная Radeon 760M; скорость ещё неизвестна.
- **Рассмотренные варианты:**
  1. FTS5 + локальные эмбеддинги через llama.cpp — сочетает точные слова и смысл, работает офлайн; увеличивает размер THIN и время индексации.
  2. Только FTS5 — маленькая поставка и простой прототип, но слабее для перефразирования.
  3. Внешние эмбеддинги — меньше локальных вычислений, но отправляют документы и несовместимы с LocalOnly.
- **Решение:** Гибридный поиск в MVP: FTS5 + Qwen3-Embedding-0.6B GGUF Q8_0 (1024, pooling last, нормирование). Для генерации FAT — Qwen3-4B GGUF Q4_K_M через тот же runtime на CPU, без thinking. Реальные профили модели/токенизации/параметров версионируются.
- **Причины:** Карточки автора описывают GGUF и llama.cpp, многоязычность и Apache-2.0; ссылки приведены в ARCHITECTURE.md. Это основания для эксперимента, а не доказанная точность на наших документах. Общий runtime уменьшает число технологий.
- **Последствия:** THIN тоже содержит локальный движок эмбеддингов. Локальные веса импортируются/поставляются заранее, без скрытой загрузки. До измерений 16 ГБ — целевой ориентир, 5 минут — гипотеза. Точный перебор не ограничивает файлы числом 30. Более крупная модель или GPU-ускорение выбираются только по результату испытаний. На этапе 3 достаточен KeywordRetriever, он не выдаётся за готовый смысловой поиск.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-012 — Windows, Qt Widgets и поставка без терминала

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** 26.10.2026 выбраны Windows 10 и 11; Qt уже выбран, GUI должен оставаться отдельным слоем.
- **Рассмотренные варианты:**
  1. Qt Widgets + каталог EXE/DLL/весов — привычный desktop-интерфейс, одна C++-среда; несколько файлов в поставке.
  2. Qt Quick/QML — гибче визуально, но дополнительный язык и механизм связывания.
  3. Статическая сборка в один EXE — выглядит проще для пользователя, но осложняет сборку/лицензионные обязательства и не устраняет файлы весов.
- **Решение:** Qt Widgets, Windows x64; исходная линия Qt 6.10.x + MSVC 2022. Динамические Qt DLL, windeployqt, переносимый каталог в архиве; запуск EXE, при необходимости установщик позже.
- **Причины:** Таблица платформ Qt 6.10 включает Windows 10 (1809+) и Windows 11 x64. Перед фиксацией patch-версии совместимость проверяется повторно; собственная поддержка подтверждается только испытаниями.
- **Последствия:** Основной путь Qt — LGPLv3, без предположения, что цена 15 000 ₽ автоматически даёт коммерческую лицензию Qt. Проверить notices, исходники используемого Qt, заменяемость DLL, транзитивные лицензии и условия собственной лицензии. Qt только в Presentation; сетевой адаптер — WinHTTP. Точная сборка/runtime и упаковка проверяются на чистых ОС до MVP. Установка Qt пока не выполнялась.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-013 — Очередь операций, отмена и согласованность

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** Нужно избежать гонки между отправкой контекста, сменой политики и обновлением индекса, сохранив отзывчивость GUI.
- **Рассмотренные варианты:**
  1. Один рабочий исполнитель на библиотеку — простой порядок операций и согласованность; нет параллельных вопросов.
  2. Параллельные запросы и индексирование — выше пропускная способность, но сложнее ревизии, отмена и инвалидация.
  3. Всё в UI-потоке — проще код, но окно зависает при чтении/генерации.
- **Решение:** В MVP открыта одна библиотека, один активный вопрос/импорт вне UI-потока, снимок ревизии на операцию. Смена библиотеки/режима/политики/документов ждёт завершения или отмены работы. Единственный владелец БД.
- **Причины:** Для гипотезы 20 вопросов в день параллелизм не оправдывает сложность. Стабильный снимок позволяет воспроизводить кэш и проверять разрешения.
- **Последствия:** Отмена распространяется в reader, генератор и HTTP; начальный deadline 300 секунд — предел ожидания, не обещание скорости. Автоматических повторов после возможной отправки платного запроса нет. Состояние «локально» показывается после остановки сетевой работы; уже отправленные данные не отзываются. Отмена/сбой импорта не публикуют частичную ревизию.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».

## ADR-014 — История самостоятельных вопросов

- **Дата и статус:** 26.10.2026 — **принято для проектирования**; не реализовано. Результат зафиксирован в `v0.2`.
- **Контекст:** Термин «история диалога» допускает разные ожидания. 26.10.2026 выбрано сохранение истории без учёта переписки моделью.
- **Рассмотренные варианты:**
  1. Самостоятельные вопросы + сохранённая история — понятные источники и ключ кэша; надо повторять контекст вопроса.
  2. Контекстный чат — удобны уточнения «а этот пункт?», но история меняет поиск, кэш и разрешения на передачу.
  3. Не сохранять историю — меньше данных, но не соответствует MVP.
- **Решение:** Первый вариант. История для просмотра хранится локально; предыдущие сообщения не включаются в поиск/промпт. UI явно объясняет самостоятельность вопросов.
- **Причины:** Выбранный сценарий и простое проверяемое правило кэша. Ответы по LocalOnly не могут незаметно уйти в API через историю.
- **Последствия:** Просмотр старого ответа показывает его ревизию/модель и устаревание при смене индекса. Расширение до контекстного чата требует нового ADR, учёта истории в ключе и проверки доступа ко всем её источникам.
- **Связанные коммиты и версии:** версия `v0.2` от 26.10.2026, коммит «Описана архитектура приложения».
