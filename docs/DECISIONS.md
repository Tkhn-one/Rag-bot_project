# Реестр архитектурных решений

Формат ADR соответствует приложению Б методички. Ниже сохранены ранее подготовленные варианты; статус «предложено» не означает, что выбор утверждён. Даты, причины и последствия заполняются при принятии решения на этапе 2. ADR-007 и ADR-008 обозначены как принятые в существующем черновике; дату и основание их принятия ещё нужно подтвердить.

---

## ADR-001 — Язык и стек проекта

- **Дата и статус:** дата не зафиксирована — предложено
- **Контекст:** методичка требует C++11+; другие языки допустимы только по согласованию с преподавателем. Предшествующий прототип реализован на Python (Streamlit).
- **Рассмотренные варианты:**
  1. C++20 + CMake — соответствует требованиям по умолчанию.
  2. Python — быстрее в разработке, но требуется согласование языка и перенос части требований (CMake и т. п.).
- **Решение:** не принято; по умолчанию методички — C++20 и CMake, Python требует согласования.
- **Причины:** уточняются после выбора языка.
- **Последствия:** выбор определит сборку и допустимый GUI.

## ADR-002 — Разделение на слои

- **Дата и статус:** дата не зафиксирована — предложено
- **Контекст:** требуется отделить бизнес-логику от интерфейса, чтобы GUI был расширением, а не переписыванием (раздел 5 методички).
- **Рассмотренные варианты:**
  1. Слои Domain / Application / Infrastructure / Presentation / Tests.
  2. Монолит с последующим выделением слоёв — быстрее первый прототип, но грозит переписыванием при добавлении GUI.
- **Решение:** предложен вариант 1; утверждение ожидается на этапе 2.
- **Причины:** границы слоёв позволяют заменить UI и хранилище без изменения правил предметной области.
- **Последствия:** потребуется согласовать интерфейсы между слоями.
- **Связанные коммиты и версии:** —

## ADR-003 — Платформа GUI

- **Дата и статус:** дата не зафиксирована — предложено
- **Контекст:** преподаватель требует приложение для обычного пользователя (не «питон-бэкендер»); язык курса по умолчанию C++11+; GUI по методичке — расширение архитектуры, а не замена.
- **Рассмотренные варианты:**
  1. **Qt 6 + CMake (C++)** — нативно для языка курса, один бинарник, кроссплатформенно, встраивается в текущую структуру слоёв, легко упаковать локальную модель в FAT-сборку.
  2. **Tauri/Electron + C++ ядро** — красивый веб-UI, но смешанный тулчейн и больше работы по интеграции.
  3. **PySide6 (Python)** — быстрее в разработке, но требует согласования языка с преподавателем.
- **Решение:** не принято; варианты требуют сравнения после выбора языка.
- **Причины:** уточняются по результату выбора.
- **Последствия:** Presentation-слой заменяем, Domain/Application не трогаем.
- **Связанные коммиты и версии:** —

## ADR-004 — Провайдер LLM и две сборки

- **Дата и статус:** дата не зафиксирована — предложено
- **Контекст:** требование преподавателя — два варианта приложения (внешний API и встроенная llama) без дублирования кода; выбор нейросети должен быть заменяемой деталью.
- **Рассмотренные варианты:**
  1. Интерфейс `ILlmProvider` + реализации `RemoteApiProvider` (OpenAI-совместимый: GPT/DeepSeek/Grok/OpenRouter), `LocalLlamaProvider` (llama.cpp + GGUF), `MockProvider` (тесты). Сборки через CMake-опцию `WITH_LOCAL_LLM=ON/OFF`.
  2. Две отдельные кодовые базы — отвергнуто: дублирование и расхождение логики.
- **Решение:** предложен вариант 1; окончательный выбор ожидается на этапе 2.
- **Причины:** полиморфизм закрывает требование ООП; один код — два продукта; тесты идут на Mock без сети.
- **Последствия:** вес FAT-сборки и требования к ПК выше (веса GGUF — гигабайты); нужна проверка лицензии выбранной модели для распространения весов.
- **Связанные коммиты и версии:** —

## ADR-005 — Кэш ответов как контроль себестоимости

- **Дата и статус:** дата не зафиксирована — предложено
- **Контекст:** требование преподавателя: один и тот же вопрос не должен порождать новый запрос к платному API; при монетизации это прямые расходы.
- **Рассмотренные варианты:**
  1. **Декоратор `CachingLlmProvider` над `ILlmProvider`** — прозрачно для Application, легко тестируется счётчиком вызовов.
  2. Кэш внутри `RemoteApiProvider` — отвергнуто: логика кэша смешивается с транспортом и не работает для локального провайдера.
  3. Кэш в UI — отвергнуто: обходится любым другим клиентом, не тестируется.
- **Решение:** предложен вариант 1; ключ = hash(нормализованный вопрос + версия индекса + id модели); инвалидация при изменении документов или модели. Способ хранения выбирается на этапе 2.
- **Причины:** кэш становится отдельной обязанностью класса, а не «оптимизацией внутри кода».
- **Последствия:** нужен счётчик «сэкономленных» вызовов (для демонстрации на защите и для метрик продукта); важна корректная инвалидация.
- **Связанные коммиты и версии:** —

## ADR-006 — Хранение индекса

- **Дата и статус:** дата не зафиксирована — предложено
- **Контекст:** индекс (чанки + эмбеддинги) должен сохраняться между запусками и не требовать серверной БД; предыдущий прототип использовал ChromaDB (Python-сервис).
- **Рассмотренные варианты:**
  1. **SQLite (метаданные и чанки) + файл векторного индекса** (hnswlib/usearch) — локально, без сервера.
  2. Встроенный FAISS — мощно, но тяжелее в сборке под Windows.
  3. Продолжать использовать ChromaDB — серверная зависимость, плохо совместима с «обычной программой» для пользователя.
- **Решение:** не принято; вариант хранения нужно проверить после выбора языка и зависимостей.
- **Причины:** уточняются по результату сравнения вариантов.
- **Последствия:** абстрагировать доступ интерфейсом репозитория — на защите спросят «как заменить хранилище, не переписывая логику».
- **Связанные коммиты и версии:** —

## ADR-007 — Модель монетизации: разовая покупка + ключ пользователя

- **Дата и статус:** дата не зафиксирована — **принято**
- **Контекст:** у части пользователей документы нельзя передавать третьим лицам, поэтому нужен офлайн-режим; при этом продавать подписку со своими ключами сейчас нельзя — ключи, зашитые в десктопный клиент, извлекаются, а сервер-прокси требует отдельной инфраструктуры.
- **Рассмотренные варианты:**
  1. **Разовая покупка + ключ пользователя (BYO-key)** — вендор не платит за токены, локальный режим вообще без затрат.
  2. Подписка с вендорским API — нужен сервер-прокси и защита ключей; расход на токены попадает в себестоимость.
- **Решение:** вариант 1. Вариант 2 — вне рамок текущей версии.
- **Причины:** нулевая себестоимость у вендора; офлайн-сборка продаётся как «конфиденциальное издание»; нет ответственности за чужие данные на наших серверах.
- **Последствия:** пользователю требуется получить ключ самостоятельно; это компенсируется онбордингом и локальным режимом без затрат на API. Кэш (ADR-005) экономит средства пользователя и входит в ценность продукта.
- **Связанные коммиты и версии:** —

## ADR-008 — Границы доверия и режим «Только локально»

- **Дата и статус:** дата не зафиксирована — **принято**
- **Контекст:** часть документов запрещено передавать третьим лицам. Продукт обязан физически, а не декларативно, гарантировать, что такие документы обрабатываются локальной моделью.
- **Рассмотренные варианты:**
  1. **Политика обработки у библиотеки/документа** (`LocalOnly` / `AllowRemote`), проверяемая в единственной точке выбора провайдера в Application-слое; попытка нарушить политику — ошибка с понятным сообщением.
  2. Предупреждение в UI («вы уверены?») — отвергнуто: при «защите от дурака» предупреждения обходятся по привычке.
  3. Разные сборки с разным кодом — отвергнуто: дублирование логики, риск регрессии.
- **Решение:** вариант 1. Содержимое документов не попадает в логи; телеметрия выключена по умолчанию; способ хранения ключа выбирается в ADR-009. Обязателен автоматический тест «ноль сетевых вызовов» при локальном провайдере.
- **Причины:** проверяемость. На защите продукт демонстрируется через монитор сети: документ «только локально» — ни одного исходящего соединения.
- **Последствия:** нужен слой политики поверх `ILlmProvider` (в Application), он же используется для отображения статуса в UI («документ закрыт: обрабатывается на этом компьютере»); любая новая функция с сетевыми вызовами обязана уважать политику.

## ADR-009 — Хранение API-ключа пользователя

- **Дата и статус:** дата не зафиксирована — предложено
- **Контекст:** пользователь вводит свой ключ; хранение в открытом файле конфигурации или в репозитории недопустимо (методичка прямо запрещает секреты в репозитории, п. 9).
- **Рассмотренные варианты:**
  1. **Системное хранилище секретов** (Windows Credential Manager / macOS Keychain / libsecret) — ключ не лежит в открытом виде.
  2. Файл конфигурации с ограниченными правами — проще, но читается любым процессом пользователя.
  3. Переменная окружения — удобно для разработки и CI, неудобно обычному пользователю.
- **Решение:** не принято; предложено системное хранилище с переменной окружения для разработки.
- **Причины:** системное хранилище лучше подходит обычному пользователю, чем открытый конфигурационный файл; решение требует проверки после выбора платформы.
- **Последствия:** ключ маскируется в логах (`sk-...abcd`), никогда не выводится в интерфейсе полностью.
