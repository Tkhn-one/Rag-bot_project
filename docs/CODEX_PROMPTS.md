# CODEX_PROMPTS.md — промпты по этапам и экономия лимитов

Принцип: требования и правила хранятся в файлах репозитория; в чат отправляются ссылки на них.
Промпт = `@файл` + одна задача + критерий приёмки.

## Часть 1. Правила экономии лимитов

| # | Правило | Эффект |
|---|---|---|
| 1 | Требования и правила — в `AGENTS.md`, `docs/PROJECT_BRIEF.md`, `docs/METODICHKA.md`. В промпте — только `@ссылки`. | Меньше текста в каждом сообщении |
| 2 | Одна задача = одно сообщение = один результат (изменённые файлы, команды, вывод тестов). | Без повторных проверок |
| 3 | Модель под задачу: планирование — Sol @ High, код — Terra @ Medium, документация — Luna @ Low. Ultra — на этапе сборки MVP. | Основную работу выполняет недорогая модель |
| 4 | Объяснения — по одному модулю и перед защитой, а не по всему проекту в процессе разработки. | Экономия на самом дорогом выводе |
| 5 | Область задачи указывать точно: `src/domain/**` вместо «весь проект». | Меньше входного контекста |
| 6 | Документация создаётся на своём этапе, а не «на будущее». | Без лишних файлов |
| 7 | Проверка — тестами: «покажи команду и вывод», а не «проверь ещё раз». | Без двойной работы |
| 8 | Решения — в `docs/DECISIONS.md`; новый чат начинается чтением этого файла. | Дешёвое возобновление работы |
| 9 | Новый чат — на каждый этап (0–6); внутри этапа — один чат. | Контекст не переносится зря |
| 10 | Правка фрагмента вместо генерации файла целиком: «правь только X, остальное не трогай». | Меньше вывода и лишних правок |

Расход токенов отображается в Codex → Профиль. На тарифе Plus лимит общий с ChatGPT Work.

## Часть 2. Промпты

### 0. Онбординг

```
Прочитай @AGENTS.md, @docs/METODICHKA.md, @docs/PROJECT_BRIEF.md.
Перечисли 5 обязательных требований методички, которые чаще всего нарушают,
и задай вопросы, нужные для этапа 1. Код не пиши.
```

### 1. Product brief (тег v0.1)

```
По @docs/PROJECT_BRIEF.md проверь и уточни @docs/PRODUCT.md: пользователь,
проблема, границы MVP, аналоги.
Монетизация: вариант A (разовая покупка + ключ пользователя), уточнения не требуются.
Затем: строка в @CHANGELOG.md и текст коммита.
```

### 2. Архитектура (тег v0.2)

```
Предложи 2 варианта архитектуры под @docs/PROJECT_BRIEF.md (раздел 5 методички):
слои, классы, зависимости, хранение индекса, где полиморфизм и почему.
Требования: GUI заменяем без правок логики; провайдер LLM заменяем;
кэш встраивается между Application и провайдером.
Зафиксируй выбор в @docs/ARCHITECTURE.md и ADR в @docs/DECISIONS.md. Код не пиши.
```

### 3. Вертикальный срез (тег v0.3)

```
Реализуй вертикальный срез: загрузка одного TXT → чанки → ответ с цитатой →
вывод в CLI. Провайдер — MockProvider (без сети). Тест на сценарий.
Область: src/domain, src/application, src/presentation/cli, tests.
Затем CHANGELOG и текст коммита.
```

### 4. Кэш ответов

```
Добавь CachingLlmProvider как декоратор над ILlmProvider:
ключ = hash(нормализованный вопрос + версия индекса + id модели), хранилище — SQLite.
Тесты: повторный вопрос даёт 0 сетевых вызовов; новый документ инвалидирует кэш.
Область: src/application, src/infrastructure, tests. Отчёт: файлы, команды, вывод.
```

### 5. Приватность: режим «Только локально»

```
Добавь политику обработки: у документа/библиотеки флаг LocalOnly / AllowRemote.
Решение о провайдере принимается в одной точке Application-слоя.
LocalOnly + удалённый провайдер = ошибка с понятным сообщением, не предупреждение.
Тесты: (1) локальный провайдер — счётчик сетевых вызовов равен 0;
(2) LocalOnly-документ не может уйти в RemoteApiProvider;
(3) текст документа не попадает в логи.
Область: src/application, src/infrastructure, tests.
```

### 6. Провайдеры и две сборки

```
Добавь RemoteApiProvider (OpenAI-совместимый: GPT/DeepSeek/Grok, ключ из системного
хранилища) и CMake-опцию WITH_LOCAL_LLM=ON/OFF.
ON — бизнес-логика не меняется; OFF не тянет зависимости llama.
Тесты: провайдеры взаимозаменяемы через интерфейс.
```

### 7. GUI

```
Реализуй GUI-слой поверх существующих Application-сервисов: окно, добавление файлов,
список истории, поле вопроса, панель цитат.
Бизнес-логику и Domain не менять. Если для GUI требуется правка логики —
остановись и покажи, что именно пришлось бы менять.
```

### 8. Первый запуск и ключ API

```
Добавь первый запуск: экран выбора режима («Внешний API» / «Только локально, без интернета»),
ввод ключа с сохранением в системное хранилище секретов (не в открытый конфиг),
понятный текст при неверном ключе. Ключ в логах маскируется.
Тесты: сохранение и чтение ключа, маскирование, сообщение об ошибке.
```

## Часть 3. Расход лимитов: чего избегать

- Пересказ требований в чате вместо ссылок на файлы.
- Запросы «посмотри весь проект и предложи улучшения» — широкие и дорогие.
- Подробное объяснение каждой строки в процессе разработки (объяснения — перед защитой, по модулям).
- Один чат на весь семестр: контекст растёт, каждый запрос дорожает.
- Повторные ревью одного и того же кода.
- Ultra и Max на простых задачах.
- Запросы «сделай сразу всё» (например, весь GUI одним сообщением).
