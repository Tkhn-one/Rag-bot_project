## 27.11.2026 — Жизненный цикл документа (этап 5, шаг 1б)

**Контекст.** Студент принял шаг 1а, коммит `35b3b9a` опубликован. Для неизвестного контекста выбрано блокирование удаления до отдельной подтверждённой очистки.

**Решение.** Сохраняются неизменяемые ID версий и общая группа документа. Предыдущие версии остаются для цитат. Состав контекста фиксирует валидирующий декоратор после сокращения до бюджета провайдера. Для кэша, полученного до миграции, состав остаётся неизвестным и при повторе. Изменение ревизии исключает использование устаревшего кэша; несвязанные записи сохраняются. При удалении набор записей вычисляется по всем версиям группы под блокировкой SQLite.

**Проверка.** Вручную мигрирована база, созданная CLI схемы 10. До очистки команда удаления вернула блокировку с количеством записей, предпросмотр ничего не удалил. После отдельного подтверждения очистки и подтверждения удаления файл и документ исключены. Дополнительно CLI с реальными локальными эмбеддингами вернул прежнюю цитату после обновления, нашёл новый срок и после удаления сообщил о недостатке подтверждений. Регрессионный тест проверяет откат обновления, сохранение источника старой цитаты, связи с непроцитированным документом, обрезку контекста по бюджету, сбой после публикации файла и повтор очистки занятой копии. Шаг принят студентом 27.11.2026.

## 27.11.2026 — Исходная копия для цитаты (этап 5, шаг 1а)

**Задача.** Сохранить файл, с которого построен индекс, и обеспечить просмотр цитат старой библиотеки после миграции.

**Предложение и проверка.** Раньше SQLite объединял записи по извлечённому тексту и разметке. У TXT с BOM и без него эти значения совпадают при разных исходных байтах. Для постоянной библиотеки реализована идентификация по SHA-256 байтов. В тесте внешний файл изменяется во время импорта, а парсер читает временную копию. После перезапуска проверяются исходные байты, текст и координаты цитат TXT, PDF и DOCX. При ручной проверке перенос исходного TXT сохранил доступ к строке 4, независимая проверка Windows подтвердила SHA-256 копии.

**Результат для ревью.** База, созданная прежним CLI со схемой 9, открылась в схеме 10. Для цитаты доступны сохранённый текст и статус отсутствующей исходной копии. Повторный вопрос вернулся из кэша. Решение и его границы описаны в ADR-010. Шаг принят студентом и опубликован коммитом `35b3b9a`.

## 24.11.2026 — Ответы локального генератора по документам LocalOnly

- **Контекст и запрос** — подключить Qwen3-4B Q4_K_M к тому же сценарию вопросов, что и OpenAI. На двух демонстрационных TXT требовалось проверить ответ на перефразирование, отказ при недостатке сведений и повтор из кэша.
- **Предложение ИИ** — запускать генератор на CPU через llama.cpp b6500 с отключённым thinking. Грамматика GBNF задаёт допустимую структуру JSON. Общий валидатор сверяет ID фрагмента и дословную цитату перед записью результата в кэш. Для поиска используется отдельная модель Qwen3-Embedding-0.6B.
- **Проверка ответа** — на вопрос «В какой день делают страховочную копию данных проекта?» модель ответила «пятницу» и процитировала строку 4 из `decisions.txt`. На вопрос о пароле она вернула `insufficient_evidence`, хотя поиск нашёл семь фрагментов. Повтор перефразирования в открытом процессе занял 0,145 с и обошёлся без вызова генератора. Валидатор отклонил подменённую цитату.
- **Проверка приватности** — при локальном импорте, вопросе, повторе и просмотре истории счётчики показали ноль HTTP-вызовов и чтений ключа. В отдельном прогоне наблюдатель сделал 2021 снимок таблиц TCP/UDP при импорте, вопросах и чтении истории. Сокетов процесса CLI в снимках не обнаружено. Подробные замеры и границы наблюдения приведены в [README](../README.md#проверка-на-двух-txt-24112026).
- **Принятое решение** — использовать локальный провайдер в сборке FAT. Проверка цитат, кэш и история остаются общими для обоих генераторов. Проверка проведена 24 ноября, реализация зафиксирована 26 ноября в коммите [4028245](https://github.com/Tkhn-one/Rag-bot_project/commit/40282456a121b3465151cade769e14c565ace8e3).

## 24.11.2026 — Ложная сумма на границе фрагмента

При ревью обнаружено, что после исправления длинных строк поиск по `15000` возвращал часть числа `150000`. На коммите `49cb4db` ошибка воспроизвелась в CLI на строке с 395 байтами перед суммой. Первый фрагмент закончился на пятой цифре. Проверка подстроки по координатам проходила, хотя FTS5 воспринимал обрезанное число как самостоятельный термин.

Для выбора конца фрагмента и начала перекрытия использованы позиции токенов `unicode61` в исходном блоке. Это покрывает числа, кириллицу и соседство со знаками препинания. Регрессионный тест проверяет отсутствие ложного совпадения с обоих краёв, положительный поиск полной суммы, координаты цитаты после перезапуска и лексическую часть гибридного индекса после переиндексации.

**Решение по итогам ревью.** Принято разбиение по границам терминов FTS5 с обеих сторон фрагмента. Части термина длиннее бюджета исключены из лексического индекса. При переходе на схему 8 FTS5 перестраивается из исходных блоков, а гибридный индекс обновляется через `--reindex` с моделью эмбеддингов. Исправление и регрессионные проверки вошли в [493556b](https://github.com/Tkhn-one/Rag-bot_project/commit/493556bf1b19194ac28bd377dd64006bf2cd80b7).

## 24.11.2026 — Длинная строка и проверка контекста при перефразировании

При ревью промежуточного коммита `4b594e4` воспроизведён отказ гибридного импорта на TXT с одной строкой длиннее 2048 токенов. Предыдущие 42 теста проходили в обеих конфигурациях. Регрессионный тест отдельно проверяет совпадение каждого фрагмента с подстрокой оригинала, полноту покрытия, перекрытие и цитату после повторного открытия библиотеки.

В исходном опыте для перефразирования заранее была выбрана строка «Резервное копирование выполняется каждую пятницу.». Строка заняла второе место по косинусу и третье в итоговом контексте. ## 10.11.2026 — Вертикальный прототип

**Контекст:** после проектирования требовалось проверить один сценарий через все слои приложения. Инструменты MSVC, CMake и CTest были установлены и проверены на пробной программе C++20.

**Запрос к ИИ:** выполнить этап 3 по методичке и плану проекта.

**Предложение ИИ:** использовать одну непустую строку TXT как фрагмент и хранить индекс в памяти. Поиск по словам выбирает строку с наибольшим числом совпадений. Тестовый провайдер возвращает её текст, а сценарий проверяет номер строки и цитату перед выводом.

**Проверка:** прототип собран с MSVC 2022. Прошли восемь тестов CTest, включая пустой ввод, отсутствие совпадений, отклонение неверной цитаты и проверку кодировок. Преобразование заменено проверяемым переводом в UTF-8, повторная сборка и тесты прошли.

**Принятое решение:** для демонстрации использовать консольный сценарий на учебном договоре. Строчное разбиение сохраняет точную позицию цитаты и позволяет проверить цепочку с минимальным индексом.

**Фиксация:** коммит «Добавлен вертикальный прототип поиска по TXT», контрольная версия `v0.3`. Запуск показан в ходе проверки, отдельное предъявление преподавателю не зафиксировано.

## Формат записи

```markdown
## ДД.ММ.ГГГГ — краткое название задачи

**Контекст:** что требовалось решить
**Запрос к ИИ:** краткий промпт или ссылка на сохранённый фрагмент
**Предложение ИИ:** суть ответа без многословного копирования
**Проверка:** сборка, тест, эксперимент, документация, сравнение вариантов
**Решение:** принято / изменено / отвергнуто, потому что ...
**Фиксация:** хеш или ссылка на коммит
```

## Правила

- Записываются только эпизоды, повлиявшие на архитектуру, реализацию, тесты или устранение ошибок.
- Ошибочные предложения ИИ фиксируются отдельной записью с указанием, как ошибка обнаружена (раздел 13 методички).
- Записи ведутся по факту работы; вымышленные или восстановленные задним числом эпизоды недопустимы (п. 7.2 методички).
- Ссылки даются на коммиты и файлы, а не на пересказ переписки.
